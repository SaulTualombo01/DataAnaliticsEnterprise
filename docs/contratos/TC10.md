# TC-10: interfaz administrativa y contexto real

Incremento Q2 del 14 de noviembre de 2026, en modulo0_troncoComun.
La interfaz compartida React consume la sesión, capacidades y operaciones
administrativas del monolito. El modo de demostración Q1 sigue siendo explícito
y separado; una caída de la API real nunca activa fixtures.

## Funciones integradas

- Acceso/cierre de sesión por cookie HttpOnly, CSRF y activación de una
  invitación. La activación no inicia sesión ni asigna un proyecto/rol.
- Sistema: crear/listar empresas, consultar/editar el nombre/desactivar cuentas
  y designar/revocar administradores empresariales según permisos vigentes.
- Empresa: proyectos (alta, nombre, archivo/reapertura), empleados,
  invitaciones, pertenencia empresarial y participantes de proyectos.
- Rol funcional único por proyecto, alcance explícito PROJECT o hasta 50
  SOURCE/ASSET, sustitución con referencia de concurrencia, historial y
  revocación concreta. SOURCE/ASSET requieren el proveedor público del módulo
  propietario; TC aislado rechaza referencias que no puede verificar.
- Proyectos propios paginados, selección persistida en sesión y permisos
  efectivos del proyecto de trabajo. Administrar una empresa no incorpora al
  administrador a sus proyectos ni concede lectura de contenido M1.

El proyecto administrado y el proyecto de trabajo son selecciones distintas.
El catálogo real toma el proyecto de la sesión: la pantalla solo solicita el
identificador del activo. El backend de esta rama TC todavía no incorpora las
dos rutas de catálogo de M1-04; integrarlas y probarlas conjuntamente es un
paso posterior. M2/M3/M4 mantienen espacios de navegación pendientes.

## Soporte HTTP añadido

Participación evoluciona de 1.0.0 a **1.1.0**, conservando formas existentes.
Los tres archivos originales 1.0.0 quedan en archive/participacion-1.0.0.
No cambia el intercambio M1/TC13 1.0.0 ni requiere otra migración SQL.

| Operación | Resultado y autorización |
| --- | --- |
| GET /api/v1/auth/administration?organization_id=UUID | Capacidades propias: platform_permissions, companies, selected_organization y organization_permissions. Sesión/SELF vigentes; empresa ajena devuelve404 uniforme. Sin consulta, selected_organization es null. |
| GET /api/v1/organizations/{org}/projects/{project}/memberships/{member}/role | Asignación funcional vigente con sus alcances; exige tc.company.roles.read y jerarquía real. Sin asignación devuelve404. No sustituye el historial paginado. |

La administración delegada se descubre incluso sin membresía de proyecto.
No se devuelven roles globales para que el navegador deduzca privilegios.
Las capacidades son una foto de lectura: cada operación vuelve a autorizarse
en el servidor. Las empresas inactivas no reciben capacidades ordinarias.
OpenAPI/Schema/ejemplos: participacion.*.json; cuentas permanece1.1.0 y
contexto2.0.0. Se conservan correlación, data/meta, Problem Details y no-store.

## Estados, concurrencia y manejo de información

Cambiar de cuenta/empresa/proyecto descarta consultas anteriores. Revalidar al
recuperar el foco mantiene la navegación administrativa oculta durante la
consulta; un error o pérdida de acceso elimina el contenido retenido.
Cerrar sesión desmonta los datos de la cuenta.

Formularios con motivo, confirmación y bloqueo de doble envío; las escrituras
no se reintentan automáticamente. Un409 conserva la propuesta y requiere
revisar/actualizar la referencia antes de volver a enviar. Un resultado de
red ambiguo invita a comprobar el estado, sin repetir silenciosamente.
Las revisiones de nombre/proyecto y expected_assignment_id vienen del servidor.

Retirar una membresía elimina su acceso efectivo. Reactivarla conserva el
historial pero necesita asignación nueva. Un proyecto archivado muestra el
aviso y solo concede las lecturas persistidas M1 expresamente autorizadas;
la interfaz no habilita procesamiento por mostrar un proyecto.

Contraseñas y códigos se limpian después de enviar; no se usan localStorage,
sessionStorage ni códigos en URL. La entrega manual de invitaciones requiere
INVITATION_MANUAL_DELIVERY_ENABLED=true, deshabilitada por defecto. El recibo
muestra el código enmascarado una sola vez; se puede revelar/copiar por acción
del usuario y se descarta al cerrar o cambiar de ámbito. No hay envío SMTP.
La recuperación de contraseña y el canal de correo real siguen pendientes.

Se mantienen colores, tipografía y navegación compartidos. Tablas con encabezados
y desplazamiento local, etiquetas explícitas, estados/errores anunciados,
diálogos nativos con foco, Escape y retorno de foco, diseño móvil. Estas
comprobaciones no constituyen una certificación de accesibilidad.

## Ejecutar y verificar

Backend: seguir README raíz (JDK24/release23, PostgreSQL dedicado y variables
DB_* propias). Solo para HTTP local usar SESSION_COOKIE_SECURE=false.
El administrador inicial se crea mediante el bootstrap documentado, no por
credenciales predeterminadas. Frontend, desde Frontend:

~~~powershell
npm ci
npm run dev
~~~

Abrir http://127.0.0.1:5173; API_PROXY_TARGET en .env.local permite otro backend.
Para demostración Q1 usar npm run dev:demo. Nunca poner secretos en VITE_*.

~~~powershell
npm test
npm run build
npm run build:demo
npm run test:e2e
~~~

La suite e2e ordinaria prueba el cliente con mocks HTTP y la demostración.
Para el recorrido adicional contra PostgreSQL/JAR reales, desde la raíz:

~~~powershell
python tools/verificar_tc10.py
~~~

Requiere dependencias npm instaladas, JDK24, Maven, PostgreSQL18 y Chromium
de Playwright o Chrome/Edge instalado. Admite JAVA_HOME, PG_BIN, MAVEN_CMD y
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH. Prepara sus tres puertos, clúster/base y
credenciales sintéticas; empaqueta el JAR, arranca su Vite y detiene únicamente
sus procesos en finally. No utiliza DB_* del operador ni migra bases existentes.

El test e2e-real/tc10.spec.ts no intercepta /api. Recorre empresa, invitación,
activación, delegación, proyecto, pertenencia, rol, contexto, aislamiento,
archivo, retiro/reingreso sin recuperación de rol, edición y último
administrador. Captura las pantallas sin códigos/contraseñas y verifica
teclado/ancho móvil. Las evidencias del verificador viven en su carpeta
temporal y Frontend/test-results; no se guardan credenciales en la memoria TIC.

La CI existente conserva el bloque ordinario de pruebas/build/navegador. El
recorrido PostgreSQL real es adicional local y no se afirma ejecutado en GitHub.
TC-11, integración M1 y TC13 real conservan sus bloques propios.
