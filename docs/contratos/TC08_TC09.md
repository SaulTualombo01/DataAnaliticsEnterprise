# TC-08 y TC-09: administración y participación

Implementación iniciada el13/11 y verificada el14/11/2026. Backend del monolito
en modulo0_troncoComun. La interfaz administrativa se integra en TC-10.

## Reglas adoptadas

- Una pertenencia empresarial activa por persona; varias membresías explícitas
  de proyectos de esa empresa. La invitación no crea participación en proyectos.
- Un rol funcional vigente por usuario/proyecto: GESTOR_CATALOGO,
  ANALISTA_CALIDAD, RESPONSABLE_GOBIERNO o ANALISTA_NEGOCIO, si el rol está activo.
  Roles administrativos se designan por sus operaciones existentes y no son
  delegables en el endpoint de rol funcional.
- Sistema y administradores empresariales necesitan permisos explícitos.
  La delegación empresarial solo gestiona su empresa y empleados ordinarios;
  no permite autoasignarse funciones, cambiar permisos globales ni administrar
  cuentas privilegiadas. Un administrador que necesite funciones de proyecto
  debe recibirlas de otro actor autorizado; para cuentas administrativas se
  requiere el sistema. Ningún administrador hereda acceso a contenido M1.
- La pertenencia laboral se administra como declaración del responsable, sin
  deducirla del dominio de correo ni verificarla contra un sistema de RRHH.
  No se añade una transferencia de empleados entre empresas.

## Edición de usuarios

GET /api/v1/admin/users/{user_id} y GET
/api/v1/organizations/{organization_id}/users/{user_id} devuelven
data.account/data.revision. PATCH en las mismas rutas admite únicamente
display_name, expected_revision y reason. El nombre se valida; una revisión
obsoleta devuelve409. No se convierten texto/decimales en revisión.

El correo de acceso, contraseña, estado y roles no se modifican por PATCH.
Correo requiere su futuro flujo de verificación; cambio de contraseña y
desactivación conservan las operaciones existentes. Un cambio efectivo
incrementa admin_revision y audita actor/motivo/recurso/correlación. Repetir el
mismo nombre con revisión actual no crea cambio/evento. El perfil refleja el
nombre nuevo sin revocar sesiones ni aumentar session_version.

## Membresías y roles

Rutas bajo /api/v1/organizations/{organization_id}:

| Operación | Ruta |
| --- | --- |
| Listar membresías empresariales | GET /memberships |
| Retirar/reactivar pertenencia empresarial | POST /memberships/{membership_id}/revocations o /reactivations |
| Consultar catálogo funcional activo y permisos disponibles | GET /functional-roles |
| Incorporar/listar empleados de un proyecto | POST/GET /projects/{project_id}/memberships |
| Retirar/reactivar membresía de proyecto | POST /projects/{project_id}/memberships/{membership_id}/revocations o /reactivations |
| Asignar/sustituir rol funcional y alcances | PUT /projects/{project_id}/memberships/{membership_id}/role |
| Consultar historial funcional | GET /projects/{project_id}/memberships/{membership_id}/roles |
| Revocar una asignación concreta | POST /projects/{project_id}/memberships/{membership_id}/roles/{assignment_id}/revocations |

Incorporar requiere user_id/reason y pertenencia empresarial activa. Una
membresía ya existente se reactiva por la operación específica, no se recrea
ni se reactiva implícitamente por POST. Reactivaciones/revocaciones llevan reason.

PUT role requiere role_code, scopes, expected_assignment_id y reason. Para alta
inicial expected_assignment_id es null explícito; para sustituir es el ID vigente
obtenido de la lista de membresías. Una referencia obsoleta devuelve409,
incluidas dos asignaciones concurrentes. La operación revoca la anterior y
crea una asignación nueva con sus alcances/eventos en la misma transacción;
un fallo revierte ambos cambios. El historial conserva las filas y alcances
anteriores. La repetición con referencia vigente y exactamente el mismo rol y
conjunto de alcances devuelve la asignación existente, sin duplicar auditoría.

scopes contiene1..50 elementos únicos resource_scope/resource_id. PROJECT usa
resource_id:null y no se combina con otros alcances. SOURCE/ASSET exigen UUID
canónico y validación de pertenencia al proyecto por el SPI público del módulo
propietario. Sin proveedor único o jerarquía confirmada se deniega404; TC aislado
no inventa recursos M1. No se exige una llamada HTTP entre componentes.

Retirar una membresía de proyecto revoca sus asignaciones; retirar la empresa
retira sus proyectos y administración empresarial, además de invitaciones
pendientes emitidas en esa empresa. Revocar delegación empresarial también
invalida sus invitaciones pendientes para evitar revivirlas tras una nueva
designación. Reactivar la empresa no reactiva proyectos; reactivar una membresía
de proyecto no recupera roles ni alcances. Una asignación retirada necesita otra
fila/autorización explícita. Revocar un ID histórico no retira una asignación nueva.

## Proyecto archivado y contexto personal

GET /organizations/{organization_id}/projects/{project_id} devuelve project y
revision. PATCH acepta name/expected_revision/reason. POST a /archivals o
/reactivations exige expected_revision/reason; revision procede del detalle.
El estado archived se distingue de inactive (suspensión heredada). Estas rutas
no saltan una suspensión inactive. Repetir el estado deseado es idempotente;
un cambio con revisión obsoleta devuelve409.

Archivar conserva IDs, roles y datos, registra auditoría y bloquea nuevas
incorporaciones, asignaciones y escrituras/procesamiento funcionales. No consulta
orígenes ni genera capturas/versiones de metadatos. Revocar accesos sigue
permitido. Reactivar el proyecto conserva las asignaciones que nunca fueron
revocadas; esto es distinto de reactivar una membresía.

autorizacion.permiso.archived_read habilita solo las lecturas M1 revisadas y
persistidas: sources.read, discovery.read, assets.read/search/fields.read,
dictionary.read, metadata.history.read, assets.diagram.read y progress.read,
con prefijo m1. La opción ER sigue no disponible por el catálogo original.
Cuenta/empresa/membresías/rol/permiso/alcance deben seguir vigentes. Una versión
anterior del diccionario también exige el permiso de historial en M1. Los
permisos nuevos y M2/M3/M4 quedan false hasta revisión de sus propietarios;
una operación no se habilita solo por terminar su nombre en read.

GET /auth/contexts lista únicamente proyectos propios activos/archivados y GET
/auth/contexts/{project_id}/permissions devuelve permisos/alcances actualmente
efectivos. Una membresía sin rol permite identificar el contexto, sin funciones.
POST /auth/context con project_id guarda una preferencia vinculada al actor de
la sesión; GET /auth/context la revalida y la borra con404 si perdió pertenencia.
Después de reactivar una membresía se selecciona explícitamente de nuevo.
La selección no concede acceso, no sustituye project_id de otras rutas ni
otorga contexto a un administrador sin membresía funcional.

## Contratos y compatibilidad

- participacion.openapi.json y participacion.schema.json: base1.0.0,19 operaciones.
- cuentas:1.1.0, cuatro rutas GET/PATCH añadidas sin modificar las respuestas
  UserResponse/UserList de1.0. Se conservan invitación, activación y bajas.
- contexto:2.0.0 por ampliar el enum de proyecto con archived. Antes de integrar,
  actualizar consumidores que validen un enum cerrado. Son archivos locales sin
  publicar; rutas existentes/api/v1 conservadas. archive guarda las versiones1.0
  de cuentas/contexto. Este cambio no altera los contratos M1/TC13 de intercambio.

Todas las escrituras requieren CSRF con la cookie TICSESSION. JSON cerrado,
UUID canónicos, query solo page/page_size en listas, éxito data/meta, errores
Problem Details, correlación y no-store. page desde1,25 por defecto/máximo100;
listas ordenadas y con has_next sin total inventado. Catálogo de roles (máximo4)
y permisos propios son colecciones acotadas por el catálogo, sin paginación.
La API no acepta actor/roles de plataforma/empresa implícitos del cliente.

## Persistencia y verificación

V6 añade revisión, estado archived,11 permisos ORGANIZATION y restricciones:
**6 roles/77 permisos**. Preserva V1..V5. Rechaza pertenencias empresariales
múltiples o roles funcionales simultáneos heredados sin resolverlos ni borrar
historial. En una base compartida revisar/respaldar los datos y programar la
migración/índices; no usar clean, reparación de checksums o borrado de duplicados.
No se migró una base real en este trabajo.

Escrituras administrativas conservan advisory lock937245813 y transacciones
con auditoría atómica. Es una estrategia conservadora del volumen inicial; no
se promete escalabilidad ilimitada ni protección frente a SQL externo arbitrario.
Los roles/membresías retirados no sobreviven a una sesión por caché de permisos.
La revocación afecta la siguiente comprobación, sin abortar trabajos ya iniciados.

Con JDK24/release23 y PostgreSQL18: tools/verificar_postgres_tc.py crea bases
temporales, prueba migración nueva/actualización V3..V6 con conflictos explícitos,
y las suites SQL/HTTP. tools/validar_contratos.py valida contratos/ejemplos y
respuestas de target/contract-evidence/participacion.json, sin claves o tokens.
M1 permanece en su rama previa: la integración y sus pruebas de regresión son
un paso separado antes de demostrar archivo con sus endpoints reales.

Para continuar según Q2: TC-10 interfaz administrativa/contexto real; TC-11
secretos, M1-05..08 fuentes/CSV y TC-12 lectura CSV real conservan su planificación.
Correo real/recuperación administrativa y funcionalidades M2/M3/M4 no se declaran
