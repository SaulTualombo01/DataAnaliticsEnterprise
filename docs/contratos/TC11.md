# TC-11 — referencias protegidas de credenciales

Contrato Java interno1.0.0, implementado el14/11/2026 en modulo0_troncoComun.
Servicio compartido para credenciales recuperables de fuentes PostgreSQL.
Las claves de acceso humano siguen siendo hashes BCrypt de identidad; este
servicio no las sustituye. No se añade una ruta HTTP de lectura de secretos.

## Límite modular

SecretosApi está en org.dataanaliticsent.TroncoComun.secretos; implementación en internal,
con puertos para persistencia/cifrado y adaptadores JDBC/JCA. El catálogo conserva
solo el UUID textual como credential_ref y no guarda usuario/contraseña en su
configuración. No se añade dependencia al código privado de M1.

ProveedorFuentesSecretos es la SPI de M1: consulta metadatos reales del servidor
y devuelve fuente/proyecto, destino y estados habilitada/retirada. La autorización
también exige ProveedorRecursosAutorizacion para verificar la jerarquía real.
Sin una respuesta única y coherente se deniega. TC aislado no inventa fuentes.

La integración en modulo1_catalogo aún debe sustituir AccesoPostgresConfigurado
y TIC_SOURCE_<REF>_USER/PASSWORD por esta API, implementar la SPI y registrar las
nuevas referencias mediante M1-05/06. No se convierten automáticamente referencias
históricas de entorno ni se copian credenciales reales. El UUID cabe en el campo
credentialRef actual (texto máximo128). Este incremento no modifica esa rama.

## Operaciones1.0.0

Todas obtienen el actor de IdentidadActualApi; no admiten actor ni permiso libre.

| Operación Java | Permiso sobre SOURCE y comportamiento |
| --- | --- |
| registrar | m1.sources.credentials.write; fuente no retirada, destino real coincidente; genera UUID y revisión1. |
| consultar | m1.sources.read; solo identidad, proyecto/fuente, revisión, estado y fechas. |
| reemplazar | m1.sources.credentials.write; revisión esperada, nuevo material explícito y destino actual coincidente; mismo UUID, aumenta revisión y estado ACTIVE. |
| deshabilitar | m1.sources.credentials.write; revisión esperada, DISABLED impide resolver/conectar; conserva contenido cifrado e identidad. |
| retirar | m1.sources.credentials.write; revisión esperada, RETIRED terminal; elimina ciphertext/nonce/key_id y conserva fila/auditoría. No requiere descifrar. |
| recifrar | m1.sources.credentials.write; cifra con la clave activa sin cambiar material, UUID ni estado; revisión aumenta. |
| usarPostgres | PROBAR_CONEXION exige m1.sources.connection.test; DESCUBRIR_METADATOS exige m1.discovery.execute. Solo fuente habilitada/no retirada y referencia ACTIVE vinculada al destino. |

Referencia es un record con id, projectId, sourceId, revision, status,
createdAt y updatedAt. Son nombres Java, no un contrato HTTP nuevo.
No contiene usuario, clave, ciphertext, nonce ni identificador de clave maestra.
Las versiones OpenAPI/Schema de M1/TC13, cuentas, contexto y participación
permanecen sin cambios.

Una fuente admite una referencia no retirada (ACTIVE/DISABLED) a la vez,
respaldada por índice único parcial. Tras retirar se puede crear otra identidad;
la anterior nunca resucita. Reemplazar es la acción explícita que habilita una
referencia deshabilitada. Recifrar mantiene DISABLED. Conflictos de revisión o
alta duplicada no pierden cambios. No se elimina la fila ni se cambia su
identidad/proyecto/fuente/fecha inicial mediante operaciones ordinarias.

## Uso por conectores

usarPostgres entrega CredencialPostgres únicamente al callback Java de un
conector confiable. El material se cierra en finally, incluso ante fallo; sus
buffers propios se limpian y no se pueden volver a consultar. Las operaciones
de alta/reemplazo también consumen y cierran el material recibido.
Los getters devuelven copias defensivas: el conector es responsable de limpiarlas
y de cerrar conexiones/Properties. No debe retornar credenciales, capturarlas
para uso asíncrono, registrarlas ni incluirlas en excepciones/respuestas.
toString de material/cifrado/entrada está enmascarado.

Se verifica cuenta, pertenencias, rol, permiso, alcance, fuente, destino,
estado/revisión antes de descifrar, antes del callback y después del resultado.
El callback se ejecuta fuera de una transacción de base (NOT_SUPPORTED); no
mantiene bloqueos SQL durante una llamada externa. Un cambio de acceso,
referencia o fuente detectado al terminar descarta el resultado. No puede
cancelar retroactivamente una conexión ya iniciada: el conector debe imponer
timeouts y M1 revalidar antes de publicar sus resultados.

Errores de callback se reemplazan por CONECTOR_FALLIDO sin causa/mensaje del
driver. Para distinguir errores funcionales en M1-06, el conector deberá
retornar un resultado seguro tipado, sin credenciales. Los códigos del servicio
son INVALIDO, NO_DISPONIBLE, CONFLICTO, CIFRADO_NO_DISPONIBLE y CONECTOR_FALLIDO.
Las denegaciones RBAC conservan AccesoDenegadoException. No hay reintento
automático de escritura ni fallback a una credencial/clave anterior.

## Cifrado y claves

AES-256/GCM/NoPadding mediante JCA del JDK, IV aleatorio de96bits y etiqueta
de128bits. Cada cifrado obtiene IV nuevo con SecureRandom. AAD incluye versión
del formato, UUID de referencia/proyecto/fuente, revisión, key_id y destino
(host, puerto, base, TLS). Alterar esos datos, IV o ciphertext impide abrirlo.
El formato de texto en claro es binario acotado (usuario1..256 y clave1..4096
unidades UTF-16), se cifra antes de persistir y se limpia en memoria al terminar.
No hay contraseña predeterminada ni clave maestra en el repositorio/base.

Configuración del proceso del backend:

| Variable | Contenido |
| --- | --- |
| TIC_SECRETS_KEY_IDS | IDs separados por coma, máximo8; cada ID [a-z][a-z0-9_]{0,31}. |
| TIC_SECRETS_ACTIVE_KEY_ID | ID de la clave utilizada para nuevas escrituras. |
| TIC_SECRETS_KEY_<ID_EN_MAYUSCULAS> | Clave de32bytes aleatorios codificada en Base64, obtenida de un almacén seguro del operador. |
| TIC_SECRETS_ALLOW_LOCAL_INSECURE | false por defecto. true admite exclusivamente sslmode=disable en localhost/127.0.0.1 para laboratorio local. |

Sin IDs/clave activa el backend puede arrancar y los usos criptográficos fallan
cerrados. Una configuración parcial, inválida o duplicada impide el arranque con
mensaje genérico, sin valores ni causas. No se generan claves distintas en cada
reinicio: se perdería la lectura de credenciales anteriores. Obtenerlas mediante
un gestor de secretos del despliegue; no ponerlas en application.properties,
VITE_*, URLs, argumentos, logs, capturas ni memoria TIC.

En operación ordinaria se exige verify-full. No se habilitan require/verify-ca
por aceptar esos valores en el tipo de destino. El servicio vincula el destino,
pero no valida DNS/salida de red ni crea conexiones: la política de destinos y
timeouts del conector debe completarse en M1-06. No es una bóveda administrada,
KMS/HSM, cifrado de disco/backups ni aislamiento frente a código malicioso con
acceso al mismo proceso. Java/JDBC pueden crear copias String que no se borran
determinísticamente; se minimizan buffers propios, no se promete borrado total
de memoria. Proteger dumps, proceso, entorno, base y transporte del despliegue.

### Rotación de clave de cifrado

1. Conservar las claves anteriores en el gestor externo. Añadir un ID/clave
   nuevo y seleccionarlo como activo al desplegar; mantener ambos en KEY_IDS.
2. Leer las referencias existentes con su key_id antiguo y ejecutar recifrar
   para cada referencia autorizada con su revisión actual. Las nuevas
   escrituras utilizan la clave activa. El recifrado no habilita referencias.
3. Verificar referencias no retiradas con key_id antiguo mediante revisión
   operativa protegida. Coordinar todo proceso/instancia y respaldos antes de
   retirar una clave antigua. No hay una tarea masiva automática en este bloque.
4. Tras la comprobación, retirar la clave anterior del proceso. Si se retira
   prematuramente, la apertura falla cerrada. Registrar una clave con el mismo
   ID pero distinto valor tampoco descifra el material anterior.

Rotar la clave de cifrado no cambia la contraseña del origen. Para cambiar
esa credencial, coordinar el cambio en PostgreSQL origen y reemplazar el
material del servicio. Deshabilitar/recifrar requieren la clave que abre la
referencia y la activa; retirar puede funcionar sin ellas.

## Persistencia y auditoría

V7 nueva crea secretos.referencia. Se conservan los checksums V1..V6,
6roles/77permisos. FK a proyecto y validación de fuente por SPI; no se añade
FK a tablas privadas de catálogo. Las mutaciones usan transacción REQUIRED:
M1 podrá crear/actualizar su fuente y la referencia en una sola transacción
de plataforma; debe confirmar esa transacción antes de intentar la conexión
externa. Así evita referencias huérfanas y mantiene el I/O fuera de bloqueos.
Restricciones acotan estados/revisiones/bytes;
índices de proyecto/fuente y clave; trigger preserva identidad/retirada.

Altas/cambios y auditoría se confirman en la misma transacción. Resolver exige
registrar el evento antes de entregar material; fallo de auditoría niega el
callback. El evento de resolución indica entrega autorizada al conector, no
éxito de la conexión externa. Auditoría contiene actor, proyecto, referencia,
acción, correlación del servidor, source_id, revisión y estado. No contiene
usuario, contraseña, ciphertext, clave maestra, destino ni texto libre del motivo.
Se exige un motivo no vacío en las mutaciones, pero no se conserva su texto
en este evento técnico para evitar incorporarlo como canal de secretos.

Retirar limpia el contenido de la fila vigente, no promete borrarlo de WAL,
respaldos o discos. El historial ordinario de cambios conserva solo eventos;
no se guardan versiones descifrables de contraseñas antiguas.
El propietario/superusuario de la base sigue teniendo control administrativo:
usar credenciales de despliegue mínimas, separar migración/ejecución y proteger
respaldos. No se configuró un despliegue productivo ni un almacén real del equipo.

## Verificación reproducible

Desde la raíz con JDK24/release23, Maven y PostgreSQL18:

~~~powershell
python tools/verificar_postgres_tc.py
~~~

Prepara clúster/puerto y bases de plataforma/actualización/origen separados,
roles no superusuario y contraseñas sintéticas por proceso. No utiliza bases
existentes. La nueva prueba abre una conexión JDBC al origen temporal usando
la referencia protegida; las SPI de fuente/jerarquía del test son sintéticas.
No se afirma integrado el descubrimiento M1 ni conectado un origen empresarial.

Pruebas unitarias: Unicode, IV nuevos, manipulación de AAD/ciphertext, claves
ausentes/incorrectas, rotación y limpieza del material. Pruebas PostgreSQL:
DTO sin secretos, recuperación autorizada, ciclo de vida, aislamiento, alcance
SOURCE, revocación/archivo, conflicto concurrente, cierre/fallo del conector,
ausencia de transacción durante I/O, rollback/fallo de auditoría y recifrado.
La actualizaciónV6→V7 conserva usuarios, asignaciones y auditoría anteriores.
El verificador detiene su clúster en finally y guarda evidencia temporal.

## Referencias técnicas del diseño

La implementación concreta es decisión técnica de este incremento, sujeta a
revisión del equipo. Se contrastó con [Cipher del JDK24](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/javax/crypto/Cipher.html)
y [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
Estas fuentes respaldan el uso de cifrado autenticado, IV distintos y gestión
del ciclo de vida; no certifican la seguridad del proyecto ni el despliegue.
