## Operaciones candidatas

| Método y ruta bajo /api/v1/projects/{project_id} | Entrega |
| --- | --- |
| POST /reads | Crea recibo y entrega registros acotados. HTTP201 significa recibo creado: comprobar execution_state y scope.complete. |
| GET /reads/{read_id} | Recibo, conteos y referencias; sin filas ni secretos. |
| GET /captures/{capture_id} | Contenido de captura existente y vigente; no relee el origen al caducar. |

El monolito usará principalmente interfaces Java/DTO equivalentes para M2/M4;
no obliga a HTTP entre módulos. Estas rutas no se añadieron a Spring Boot ni
se relajó denyAll para ejecutar el mock.

La petición contiene asset_id, metadata_version_id, field_ids, mode y límites
max_rows/max_bytes/timeout_ms. No admite actor, roles, credenciales, URL de origen,
SQL ni campos adicionales. La identidad y pertenencia proceden del servidor.

**Permisos candidatos, sin altas/concesiones en el RBAC actual:**
tc13.reads.create, tc13.content.read, tc13.captures.create,
tc13.reads.receipts.read y tc13.captures.content.read. Crear lectura, leer contenido,
conservar captura y consultar solo recibos son capacidades distintas. Metadatos
de M1 o administración de plataforma/empresa no conceden contenido automáticamente.

El servicio real deberá autorizar antes de extraer, publicar y entregar, y al
recuperar capturas. Un proyecto archivado no admite nuevas lecturas de origen;
el historial persistido requiere permisos y membresías vigentes. Una fuente
deshabilitada bloquea nuevas lecturas, conservando recibos/capturas autorizados.

## Semántica de la entrada y resultado

read_id identifica la lectura; execution_id, la ejecución; metadata_version_id,
la estructura M1. capture es null en live y parciales. Solo aparece si se pidió
y almacenó en ese entorno; lleva contexto, activo/campos/versión, vencimiento y
hash. La versión de metadatos nunca se presenta como copia del contenido.

raw_cells_v1 es una propuesta para revisar con M2. Cada fila tiene row_number
estable dentro de su lectura/captura y celdas por field_id. VALUE conserva texto
sin convertirlo al tipo esperado; NULL, MISSING y PARSE_ERROR se distinguen.
Cada conector futuro deberá definir su mapeo; no se promete conservar los bytes
originales de CSV/JSON. invalid_boolean se conserva como VALUE: una anomalía de
negocio no se convierte en error de transporte ni se elimina automáticamente.

El fixture conserva un ID duplicado, nulo, campo ausente y valor inválido. No
representa el piloto de100 clientes/20 pedidos ni una fuente real. Sus IDs/campos
corresponden al activo público de ejemplo de M1-04.

Lectura completa: COMPLETED y scope.complete=true. Vacío válido también completa,
con records[]. Un parcial usa FAILED y causa explícita; no se inventa PARTIAL
como estado técnico ni se presenta como resultado de calidad. M2 no debe producir
indicadores finales/aprobación a partir del parcial según su propuesta de piloto.
El recibo puede crearse aunque falle la lectura: HTTP201 no acredita datos completos.

returned_rows cuenta lo entregado; expected_rows solo existe con total confiable.
coverage_ratio es null con total desconocido o cero. Es cobertura técnica del
alcance, no calidad/cumplimiento de toda la población. serialized_bytes cuenta
records como JSON UTF-8 compacto. SHA-256 usa esos mismos bytes, ensure_ascii=false,
separadores coma/dos puntos y sin espacios/saltos añadidos.

## Parámetros y conservación propuestos

El mock admite hasta10.000 filas,10MiB y timeout_ms hasta60.000; usa siete días
como vencimiento de captura. Son sugerencias individuales de M2 para prueba,
**no límites comunes aprobados, SLA ni rendimiento medido**. No se prueba un
timeout de conector real. Alcanzar un límite antes de completar produce parcial.

Solo guarda datos sintéticos en RAM: hasta1.000 recibos y1.000 capturas por
proceso. Reinicio o expulsión por límite los pierde; no hay durabilidad. Al
vencer, la captura devuelve410 y sus filas dejan de estar accesibles; la referencia
permanece en el recibo mientras exista. No relee el origen ni promete reproducción
posterior. Persistencia, cifrado, retención/borrado y respaldo reales necesitan
diseño de David con Claudio; aquí no se almacenaron datos empresariales.

## Ejecutar y verificar

Desde la raíz del checkout:

```powershell
python tools/mock_tc13.py --port 8093
```

Escucha solo127.0.0.1, con X-Mock-Response:true, correlación y no-store. No autentica,
no aplica CSRF/RBAC reales y no abre fuentes. X-Mock-Scenario elige normal, empty,
partial, denied, unauthenticated, unavailable o source_disabled; es un selector
de prueba, nunca una identidad de producción. No hay CORS ni opción de escucha
externa. La petición de ejemplo está en tc13.examples.json → request_live.body.
Los IDs de recibos/capturas estáticos no se precargan en un proceso nuevo.

```powershell
python -m pip install -r tools/requirements-contracts.txt
python tools/validar_contratos.py
python -m unittest discover -s tools/tests -p test_tc13_mock.py -v
```

Las pruebas verifican HTTP/esquemas, conteos, límites, anomalías, reproducción,
vencimiento, IDs ajenos, entradas inválidas y concurrencia. Las denegaciones
simuladas no demuestran RBAC real. La futura auditoría registrará referencias y
conteos, sin contenido de negocio, contraseñas, cookies ni tokens.
